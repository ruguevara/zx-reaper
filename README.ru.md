# ZX-REAPER

**R**etro **E**ngineer **A**nything, **P**ort **E**verywhere **R**ightnow.

English version: [README.md](README.md).

Агентская обвязка (harness) для анализа и портирования игр ZX Spectrum 48.
Проект сделан только в развлекательных и образовательных целях.

## Retro Engineer Anything

Сначала реверс. Одним промптом превращает файл с игрой в уже размеченные, аннотированные и читаемые исходники, которые можно собрать обратно байт в байт, причём они по возможности перемещаемые и
без магических констант.

В комплекте получаете документацию про устройство игры: сверху вниз, вдоль и поперёк, от и до,
со ссылками на исходники, с галереей всей графики, картами уровней и найденными в оригинальной игре багами.

## Port Everywhere Right now

Затем с помощью агента также одним промптом вы можете портировать asm-исходники на Python.
Каждый этап портирования строго основывается на предыдущем шаге и тестируется попроцедурно.

Первый порт: Python с раскладкой памяти оригинала, как если бы на Python писали в модели памяти и в ограничениях ZX Spectrum. Используется фреймворк [Pyxel](https://github.com/kitao/pyxel) и ZX-подобный враппер поверх него. Это уже мультиплатформенный порт, можно запускать везде, даже в вебе.

Второй порт: уже чистая переносимая логика игры на Python и ZX-подобный слой представления (графика, звук). Работу делают ведущий агент и субагенты с помощью skill-ов, а механику — скрипты.

После чего этот слой можно менять, например, улучшить графику, сделать ремастер, ремейк. Или изменить слой игровой логики, или добавить новых уровней. Далее по желанию можете сделать порт на C/С++, Rust, JS — под какую хотите платформу.

| # | Откуда → куда | Проверка | Статус |
| --- | --- | --- | --- |
| 1 | лента → автоматический дизасм (SkoolKit) → лента | лента и снапшот совпадают побайтно | готов |
| 2 | автоматический дизасм → размеченный перемещаемый asm без магических чисел → лента | то же, плюс `make shift-test` и модели процедур (`make diff`) | готов |
| 3 | asm → Python на `zxpyxel`, заменителе железа 48K поверх [Pyxel](https://github.com/kitao/pyxel): раскладка памяти оригинала, те же экраны и поведение, код — попроцедурная калька asm | процедуры против кода Z80 (`zxdiff.py`); вся игра — воспроизведением входа из прогона на Z80 и сравнением памяти игры на каждом проходе главного цикла (`make port-test`) | готов |
| 4 | Python на `zxpyxel` → чистая логика игры над простым состоянием (без адресов, регистров и тактов), вид Spectrum сохранён, на любом фреймворке | этап 3 как оракул: каждый вызов процедуры и каждый шаг записанных прогонов, состояние, звук и экран (`make game-test`) | готов |
| 5 | логика игры → C/C++ с SDL2 или библиотеками платформы, или JS для веба | golden-прогоны этапа 4 | тривиально с агентом |

На каждом этапе проверка берёт предыдущий этап как оракула, поэтому цепочка доходит до
оригинала: этап 3 повторяет ввод, который прочитал прогон на Z80, и должен
содержать ту же память на каждом проходе главного цикла; этап 4 проверяется по этапу 3 на тех же записанных прогонах и должен приходить к тем же состояниям игровых переменных, экрана
и звукам на каждом шаге, а каждый вызов процедуры этапа 3 — это тест
для её версии на этапе 4. То, что даётся прогону трудно, становится правилом
в skill или новым тестом в инструментах. *Обвязка самообучается.*

На любом этапе можно остановиться, сделать форк и выпустить игру. Измените
Python этапа 3 или 4, сыграйте, выпустите (Pyxel собирает приложение для
десктопа или одну HTML-страницу: `make port-html`, `make game-html`) — или
вернитесь обратно на Spectrum: этап 3 сохраняет раскладку памяти оригинала и имена
процедур, поэтому изменение переносится обратно в asm попроцедурно, теми же дифференциальными тестами, запущенными в обратную сторону.

## Примеры

Три игры, в том порядке, в каком они делались. Каждый прогон
заканчивался сравнением с существующими открытыми разборами, и то, в чём прогон
ошибся, до следующей игры становилось правилом в skill или тестом в
инструментах: обвязка учится на своих прогонах и их ошибках. Каждый пример содержит
запись своего прогона.

1. **Hungry Horace** (Psion/Melbourne House, 1982),
   [`examples/hungry-horace/`](examples/hungry-horace/): эталонный прогон.
   Этапы 1 и 2 сравнены с эталонным дизасмом SkoolKit; этап 3
   совпадает с Z80 на каждом проходе главного цикла трёх записанных
   прогонов; этап 4 совпадает с этапом 3 на каждом шаге, в точном режиме
   (странности оригинала сохранены); звук проверен на слух.
   [Отчёт о прогоне](docs/hungry-horace-run.ru.md).
2. **Jet Set Willy** (Software Projects, 1984),
   [`examples/jet-set-willy/`](examples/jet-set-willy/): этапы 1 и 2,
   сравнены с эталонным дизасмом SkoolKit
   ([сравнение](examples/jet-set-willy/re/comparison.md)).
3. **The Hobbit** (Melbourne House, 1982),
   [`examples/the-hobbit/`](examples/the-hobbit/): самый свежий. Текстовое
   приключение с парсером, персонажами, которые действуют сами, и векторными
   картинками, пройдено вслепую по этапам 1–4 без участия человека, кроме
   маленького интервью этапа 4 о графике, вводе и звуке. Порт этапа 3 совпадает с Z80
   на каждом проходе главного цикла для шести записанных прогонов (один
   проходит игру до конца), игра этапа 4 совпадает с этапом 3 на каждом проходе,
   с экраном включительно; обе играются на десктопе и в браузере. Далее проведено
   сравнение с существующими проектами по дизассемблированию, с портом на C и статьёй
   соавторки игры Вероники Меглер: байты, карта кода и смысл совпадают с самым полным
   источником везде, где оба источника что-то описывают; единственный прогон перепутал названия только двух полей, пропустил 17 из 50 известных ошибок, содержащихся в оригинальной игре, и нашёл 14 новых ошибок, которых нет ни в одном источнике
   ([сравнение](examples/the-hobbit/re/comparison.md)). Ошибки перечислены,
   но не исправлены в примере;
   [отчёт о прогоне](docs/the-hobbit-run.ru.md) показывает, что каждая из
   них изменила в обвязке.
   Ошибки в названиях дёшево исправить задним числом: вторая сессия с промптом вроде «Пересмотри исходники, логику, сообщения, спрайты, графику и замени названия переменных, полей, процедур и т. п. на более корректные» должна их исправить. Её не запускали, потому что пример остаётся таким, каким его оставил прогон, а в `zx-annotate` теперь есть правило против каждой из этих ошибок. Пропущенные баги — другое дело: найти все ошибки в программе — открытая задача даже при наличии спецификации, и все источники вместе тоже пропустили 14 ошибок, которые нашёл этот прогон.

Текущие ограничения: ZX Spectrum 48K. Музыка и эффекты AY (128K) — позже, через
[pyayay](https://github.com/ruguevara/pyayay) (Ayumi). Вне рамок:
этап 5, 128K и AY, защищённые и турбо-загрузчики (такие игры лучше начинать со
снапшота, а не с ленты), игры, которым нужен тайминг с точностью до contention по памяти.

## Установка

Нужны Python 3.9 или новее, [sjasmplus](https://github.com/z00m128/sjasmplus)
(проверено с 1.20.1 и 1.24.0) и make. По желанию — Fuse: играть, записывать
RZX и на глаз сверять эффекты, которые зависят от тактов.

```sh
git clone https://github.com/ruguevara/zx-reaper.git && cd zx-reaper
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt   # SkoolKit (его скрипты попадают в PATH) и Pyxel
tools/zxdoctor.py                 # проверяет Python, SkoolKit, sjasmplus, make
selftest/run.sh                   # должен закончиться SELFTEST PASSED
```

`zxdoctor.py` для каждого недостающего инструмента печатает команду, которая
его поставит. `selftest/run.sh` собирает маленькую игру-фикстуру и проводит
её через весь конвейер без агента; если он прошёл, обвязка готова. Держите
venv активным, когда работаете в проекте игры: его инструменты импортируют
SkoolKit.

### Попробовать на примере

Примеры собираются и играются без агента. Ленты в git нет: возьмите её сами
(для The Hobbit — `HobbitTheV1.2.tzx` со Spectrum Computing) и положите в
`original/game.tzx`.

```sh
cd examples/the-hobbit
make restore          # re/tape/, re/orig.z80, re/image.z80 из ленты
make                  # должен напечатать IDENTICAL
make port-test        # этап 3: порт на Python против прогонов Z80
make game-test        # этап 4: чистая игра против этапа 3
python3 port/play.py  # сыграть этап 3 (Pyxel); python3 game/play.py — этап 4
```

Остальные проверки примера — в его [README](examples/the-hobbit/README.md).

## Новый проект

1. **Лента.** Нужен TAP или TZX игры для 48K. Блоки со стандартным
   заголовком разбираются автоматически; нестандартные загрузчики,
   безголовые и зашифрованные блоки агент разбирает по skill `zx-init`.
   Если есть запись прохождения (RZX, например из RZX Archive), передайте и
   её: она откроет код поздних уровней, до которых не доходит случайная
   игра.
2. **Проект.**

   ```sh
   python3 <zx-reaper>/tools/zxinit.py game.tzx game-re/ [--rzx play.rzx]
   cd game-re && make            # должен напечатать IDENTICAL
   git init && git add -A && git commit -m "re: init"
   ```

   `zxinit.py` копирует в проект `template/` и `tools/`, а `zxpyxel/` — в
   `port/`; разбирает ленту, симулирует загрузку, снимает карту исполнения
   случайной игрой и пишет автоматическую дизассемблировку, по файлу на
   запись (`re/skool/`). Проект самодостаточен и продолжает работать, когда
   меняется zx-reaper. С первой минуты `make` собирает ленту, побайтно
   совпадающую с оригиналом, и дальше каждая правка проверяется тем же
   `make`. Оригинальная лента в git не попадает: на другой машине положите
   её в `original/` и запустите `make restore`.
3. **Агент.** Запустите агента в каталоге проекта (`claude`) и поставьте
   задачу, например: «Пройди этапы 1 и 2 и напиши статью», потом «Этап 3:
   порт на Python», потом «Этап 4». Агент читает `AGENTS.md`, по фазам
   берёт skills из `skills/` и раздаёт пачки работы субагентам. От человека
   нужно немного: на этапе 4 ответить на интервью о графике, вводе и звуке;
   дать RZX, если покрытие упрётся в поздние уровни; в конце сыграть и
   послушать звук. Если агенты встали, обычно хватает сообщения «продолжай».
4. **Проверки.** Этап не закончен без своей проверки:

   | Этап | Проверка |
   | --- | --- |
   | 1, 2 | `make` (IDENTICAL), `make test` (хэши кадров по сценариям ввода), `make shift-test`, `make diff`, `make audit` |
   | 3 | `make port-test` |
   | 4 | `make game-test` |

5. **Играть и выпускать.** `python3 port/play.py` или `python3 game/play.py`
   — на десктопе; `make port-html` или `make game-html` собирает одну
   HTML-страницу в `build/web/` (открыть: `python3 -m http.server -d
   build/web`). Веб-сборки содержат данные игры, в git их не кладут.

Все цели `make` — в `make help`.

## Skills

Каждый skill — одна процедура с критерием готовности; он копируется в каждый
проект (`skills/`, симлинки `.claude/skills` для Claude Code и `.agents/skills` для Codex) и грузится, только когда нужен.

| Skill | Этап | Что делает | Готово, когда |
| --- | --- | --- | --- |
| `zx-init` | 1 | проект из TAP/TZX; нестандартные загрузчики, турбо, безголовые и зашифрованные блоки | `make` печатает `IDENTICAL` |
| `zx-coverage` | 1 | сценарии ввода, случайная игра и RZX, пока карта кода не перестанет расти | новые входы добавляют меньше 1% исполненного кода |
| `zx-classify` | 1 | код, данные, текст, графика и переменные порознь; карта памяти | нет данных, дизассемблированных как код |
| `zx-annotate` | 2 | имена и описания, именованные константы, самомодифицирующийся код помечен; субагенты пачками | у каждой записи есть имя и описание, находки записаны |
| `zx-relocate` | 2 | каждый адресный операнд символьный | `make shift-test` проходит при чётном и нечётном сдвиге |
| `zx-export` | 2 | skool замораживается в модули asm, `src/` становится главной копией | `src/*.asm`, по-прежнему `IDENTICAL` |
| `zx-document` | 2 | статья в `docs/` сверху вниз, с галереей, нарисованной из байтов игры | написана, прошла аудит, ссылки разрешаются |
| `zx-port` | 2, 3 | модели, которые доказывают аннотации; порт на Python процедура за процедурой против Z80 | процедуры проходят `make diff`; порт проходит `make port-test` |
| `zx-clean` | 4 | порт переписан как чистая логика над простым состоянием, ресурсы — редактируемые файлы | `make game-test` проходит против этапа 3 |

## Инструменты

| Инструмент | Назначение |
| --- | --- |
| `tools/zxinit.py` | лента → проект: разбиение, симулированная загрузка, образ, покрытие, ctl, skool, файлы сборки |
| `tools/zxrun.py` | прогон без окна на C-симуляторе SkoolKit: клавиши и Kempston по сценарию и набранный текст (`TYPE`), fuzz, карта исполнения, хэши по кадрам, скриншоты, экран как текст (`--text`, 32 или 42 колонки), POKE, вотчпоинты на запись, загрузка для теста сдвига, `--call` — вызвать процедуру игры и сохранить экран (рисует уровни для статьи), `--record` — записать чтения, прерывания и состояния в контрольных точках, которые повторяет порт, `--save-input` — сохранить fuzz-прогон как сценарий ввода |
| `tools/zxq.py` | skool, разбитый по файлу на запись; show/refs/next/status/unexec/peek/strings/gfx/reclassify/cut/check/const/equs/addrs/export; список вопросов и реестр находок, аудит |
| `tools/zxtape.py` | TAP/TZX ↔ текстовый манифест + полезная нагрузка, пересборка байт в байт, сравнение по блокам |
| `tools/zxbasic.py` | BASIC ↔ текст без потерь (скрытые числа, код в REM, странные строки) |
| `tools/zxgfx.py` | цветные листы спрайтов и тайлов, подписи и анимированные GIF из памяти, для галереи статьи |
| `tools/zxdiff.py` | дифференциальные тесты: процедура Z80 против модели на Python или функции порта этапа 3 на сгенерированных случаях по видам, с тактами (`--tstates` по видам); `--dump` пишет эталонные случаи для порта на C |
| `tools/zxcompare.py` | сравнение дизассемблировки skool с эталонной: байты, разметка, границы, документация, магические числа |
| `tools/zxport.py` | этап 3: `labels.py` и `variables.py` (типизированные метки данных) из сборки, образ RAM 48K из снапшота и проверка всей игры, которая повторяет прогоны `zxrun.py --record` |
| `tools/zxdoctor.py` | проверка готовности: инструменты, версии и чего не хватает проекту, с командой, которая это исправит |

Рабочие реестры в каждом проекте: `re/questions.md` (на что работа должна
ответить, со статусом) и `re/findings.md` (утверждения со статусом observed /
inferred / unknown / refuted и их свидетельства); они правятся через
`zxq.py question|finding`, сводку даёт `make audit`. Дисциплина
свидетельств, список вопросов и дифференциальные тесты процедур следуют
идеям [REA](https://github.com/morluto/rea) и реконструкций, сделанных с ним.

## Ограничения

- `zxrun.py` — только 48K и без contention памяти: хэши кадров проверяют
  логику, а не эффекты с точностью до такта (мультиколор, трюки с
  бордюром). Их проверяйте на глаз в Fuse или ZEsarUX.
- Повтор этапа 3 видит только прерывания IM1 из ROM; игре со своим
  обработчиком IM2 нужна контрольная точка на HALT.
- `zxinit.py` автоматизирует стандартные блоки с заголовками. Нестандартные
  загрузчики, безголовые и зашифрованные блоки разбирает skill `zx-init`
  вместе с агентом.
- `zxbasic.py` знает только ключевые слова 48K (`SPECTRUM`/`PLAY` из 128K
  выходят как `\A3`/`\A4`).
- Ленты игр защищены авторским правом: ленты и всё, что из них сделано как
  данные (снапшоты, образы RAM, извлечённые ресурсы, записи прогонов,
  веб-сборки), в git не попадают. Объяснения игр, уже разобранных публично
  (размеченные исходники, статьи, порты), публикуются без них, как примеры
  здесь.
