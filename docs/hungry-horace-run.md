# Hungry Horace — прогон метода и сравнение с SkoolKit

Полный прогон [метода](method.md) на Hungry Horace (Psion/Melbourne House, 1982) и сравнение результата с эталонной дизассемблировкой Ричарда Даймонда (skoolkit.ca, версия 2026-04-10). Эталон был скачан в отдельную папку и не открывался, пока аннотация не закончилась; субагентам запрещено было искать чужие дизассемблировки.

## Что получилось

- Исходники: 13 модулей asm (4454 строки), 2 программы BASIC, `src/constants.asm`, манифест ленты. `make` даёт ленту TZX, побайтно равную оригиналу, включая обе BASIC-программы и паузы ленты.
- 106 записей, 100% аннотированы, 166 меток; у каждой процедуры заголовок, описание, регистры, фраза `Hardware:`.
- «Магических чисел» в asm: 4 шестнадцатибитных и 34 восьмибитных литерала (было в сырой дизассемблировке 679 и 266). Оставшиеся восьмибитные — в основном номера строк и индексы в выражениях (`ATTRS+5*SCREEN_COLS`).
- Перемещаемость доказана: код, собранный со сдвигом +$7, +$101, +$1234, покадрово совпадает с оригиналом на двух сценариях (демо 3000 кадров, игра 4000 кадров).
- Графика: 15 PNG из байтов игры, карты лабиринтов и заголовок нарисованы собственными процедурами игры через `zxrun.py --call`.
- Статья в репозитории [ZX-REAPER](https://github.com/ruguevara/zx-reaper), [`examples/hungry-horace/docs/`](https://github.com/ruguevara/zx-reaper/tree/main/examples/hungry-horace/docs): 14 файлов, ~17,6 тыс. слов, 849 относительных ссылок на исходники (все проверены), диаграммы главного цикла, таблицы структур, разбор ИИ охранников с примером, галерея из 17 картинок, заметки для переноса на C/Python.
- Исходники — там же, `examples/hungry-horace/`, без ленты; положить ленту в `original/game.tzx`, затем `make restore` и `make`.

## Сравнение с эталоном

Инструмент: `tools/zxcompare.py ours.skool hh.skool --pairs pairs.tsv` (в ZX-REAPER).

**Байты.** Код совпадает полностью; 63 байта различаются в области $6DB6–$6E8E, потому что эталон обнуляет буферы переменных директивой `@defs`, а у нас — значения, загруженные с ленты. Это одна и та же версия игры.

**Разметка по байтам:**

| наше \ эталон | код | текст | данные | переменные | неисп. |
| --- | ---: | ---: | ---: | ---: | ---: |
| код | 3386 | 0 | 0 | 0 | 0 |
| текст | 0 | 123 | 0 | 0 | 0 |
| данные | 0 | 0 | 4305 | 172 | 7 |
| переменные | 0 | 0 | 0 | 103 | 0 |

Код/не код — 100% совпадение. Расхождения: четыре записи охранников (172 байта) у нас «данные», у эталона «переменные»; 7 мёртвых байт кода у нас «данные», у эталона «не используется».

**Границы процедур:** 40 из 41 общие. Эталон выделяет главный цикл $6229 в отдельную запись (у нас это метка `MainLoop` внутри `Start`); мы выделили мёртвый хвост цикла $672F.

**Смысл.** Названия всех 40 общих процедур и всех переменных описывают одно и то же; различия только в словах: `UpdateFruitDrops` / «guard drops his lunch», `BellTimer` / «guard panic timer», `HoraceDir` / «animation frame (0-3)» (кадр выбирается направлением). Примеры:

| Адрес | Наше | Эталон |
| --- | --- | --- |
| $63DA | `ChooseGuardMove` | MVGUARD: Move a guard |
| $6C20 | `GetBlockObject` | CHKATTRS: Check the attribute bytes at a sprite's location |
| $6C68 | `SaveBackground` | CPMAZEBG: Copy maze background tiles into a guard's buffer |
| $6D4E | `DrawBlocks` | BIGWORD: Print 'HUNGRY' or 'HORACE' on the title screen |
| $7C64 | `UnusedAiCounter` | TEMPVAR: Redundant temporary variable |

**Ошибки оригинальной игры:**

| Ошибка из эталона | Нашли? |
| --- | --- |
| Broken guard counter (`OR C` вместо `OR E` в $697F) | да, вплоть до исправления: эталонный POKE 27007,179 — это `OR E` |
| Free extra life | симптом найден (лишняя жизнь в начале), причина объяснена иначе |
| Game slowdown на 29-м лабиринте | при аннотации нет; на стадии статьи найдено и проверено (задержка уходит в минус на скоростях 1–3) |
| How many lives? (10 жизней печатаются как «:») | при аннотации нет; в статье как предположение; подтверждено прямым вызовом `ShowScore` (F14) |
| Who ate my lunch? (охранник подбирает предметы за другим) | нет |

Нашли сверх эталона (проверено в симуляторе): утечка стека на 2 байта при каждом выходе из демо (на 63-м выходе стек затирает код, на 70-м — сбой); «убегающий» охранник может повернуть к Хорасу из-за переполнения беззнакового байта счёта; съеденные охранники возвращаются в стартовую клетку Хораса; шаг 1 байт вместо 2 при обходе таймеров в `CheckGuardContact`; мёртвый код ($6A17, $672F, поворот охранника при звонке). Автор статьи нашёл ещё две, тоже с проверкой: на скоростях 1–3 задержка `PaceAndChime` уходит в отрицательную область и игра замирает примерно на 25 кадров каждый четвёртый проход; колокольчик, перекрывающийся с Хорасом сверху или по диагонали, начисляет 50 очков за каждый проход.

Факты эталона: переключение звука клавишей T, клавиши 1-2-3-4, ускорение после каждого 4-го лабиринта — найдены; зависимость бонуса за фрукт от направления — найдено частично.

**Стиль документирования:**

| | наше | эталон |
| --- | ---: | ---: |
| слов в заголовках и блочных комментариях | 17 424 | 2 784 |
| слов в комментариях к командам | 2 027 | 7 621 |
| прокомментировано команд кода | 18% | 60% |

Эталон — построчные комментарии и отдельные страницы (ошибки, факты, POKE-ы, звук). Наш результат — длинные описания процедур и данных, именованные константы вместо чисел, исходник, готовый к сдвигу и переносу.

После стадии статьи и прохода по реестру из пяти ошибок эталона не найдена одна — «Who ate my lunch?»; она стоит в `re/findings.md` как `unknown` (F22). Реестр находок: 18 наблюдённых, 3 выведенных, 2 открытых, 1 опровергнутое утверждение.

## Выводы для метода

1. Смысловая точность одноразового прогона на уровне эталона, который человек дорабатывал с 2014 года: имена и назначение совпали везде, где обе стороны что-то назвали.
2. Слабое место — ошибки, которые проявляются только на краях: долгая игра, двузначные счётчики, взаимодействие двух охранников. Нужен отдельный проход «охота на ошибки»: для каждого счётчика — что будет на минимуме, максимуме и переполнении; прогон симулятора с подставленными значениями (`--poke` жизней = 9, номер лабиринта = 28, скорость = 1).
3. Построчных комментариев мало (18%). Если нужен стиль эталона — поднять планку в `zx-annotate` («комментарий к каждой команде, где есть смысл в терминах игры»). Для переноса на C это не обязательно: длинные описания полезнее.
4. Найденные по ходу и исправленные дыры в kit: `@equ` до `@start` молча игнорировались; субагенты называли переменные игры через `@equ` (ломает перемещаемость) — теперь `equs --consolidate` делает из них метки; голая строка `;` внутри описания ломает skool2asm — в skill добавлено правило `; .`; один субагент сделал `rm -rf re/skool` и восстановил из копии — в skill запрет трогать общие файлы.
